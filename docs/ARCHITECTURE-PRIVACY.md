# 仓库组织与隐私边界

建议独立仓库，而不是把所有创作放进网站：

| 仓库 | 可见性 | 内容 |
| --- | --- | --- |
| creative-archive 或 USERNAME.github.io | 审核后公开 | Astro 源码、公开介绍、压缩展示图 |
| alien-language-game 等 | 按项目决定 | 游戏/程序的真实源码、issue、release |
| art-collection | 公开或私有分开建库 | 小型作品的整理记录及适合 Git 的素材 |
| creative-archive-private | Private | 未公开草稿、私人笔记、原始图、源文件、授权资料 |

私有仓库应与网站目录并列，不能位于网站仓库内部，也不要作为子模块导入部署流程。大型游戏构建用独立项目 Release、合适的试玩平台或对象存储；网站只保存公开链接与缩略图。频繁变化的 PSD、BLEND、音视频和大二进制应评估 Git LFS 或有版本/备份能力的文件存储。LFS 仍受所属仓库可见性控制，绝不是隐私措施；不要依赖 Pages 直接分发 LFS 展示资源。配额与价格启用前再核实。

## 公开与私人是两个物理边界

1. 先在私有资料库完成内容整理、图片导出与元数据清理。
2. 明确选择可公开的文字和衍生图片，复制至网站内容目录。
3. 网站只读取 `src/content/projects`，CI 只检出网站仓库，没有私有仓库 token、同步步骤或后端权限。
4. 构建拒绝 private 字段；public 目录设资源白名单；dist 再检查本地引用。
5. GitHub Pages 只上传 dist。公开网站仓库的**全部源码与 Git 历史仍然可见**，不只 dist。

`visibility` 只用于声明内容可公开，不能成为访问控制。此实现只接受 `public`，误放 private 会中止构建；这仍无法判断内容本身是否敏感。`.gitignore` 只防止常见误提交，不会保护已经被 Git 跟踪的文件。公开图库中的图片、alt、正文和说明也都公开。搜索不加载私有资料，但归档状态仍可搜索。

不要在网站仓库写密码、个人联系方式、授权密钥、未授权素材或私有链接。不要将敏感数据放进草稿后寄望“不生成页面”来隐藏它。私人资料若曾提交，不要直接把仓库改成公开；先审查完整历史，必要时由本人明确授权后处理历史与凭据轮换。

## 长期保存

- Git 记录文本变更、tag/release 记录里程碑；源文件由项目仓库或私有存储保存。
- 私有主档案至少保留另一份独立备份，定期验证能恢复。GitHub 不应是唯一备份。
- 使用开放的文字格式、稳定 slug、统一标签和可读目录；为作品记录真实日期、版本、来源与权利。
- 公开前决定网站代码许可证与作品版权。二者无需使用同一许可。
- 不活跃作品保留 `archived` 状态，不删除其历史上下文。

无需数据库：内容天然适合 Git 审阅、迁移、备份与静态生成。未来若换框架，Markdown 正文和图片依然独立可读。
